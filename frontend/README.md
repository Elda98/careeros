## Official Logo System (2026-08 — supersedes the earlier improvised palette/font)

The user supplied Orbit's official logo and brand board; the entire token system below was re-derived from it, replacing the earlier session's invented indigo/Inter system. **Brand analysis:**

| Aspect | Reading |
|---|---|
| Mark | Two intersecting orbit rings (royal purple primary, soft rose secondary) around a purple core, with satellite dots at the ring intersections — literally depicts the name |
| Primary | Royal Purple, `hsl(262 …)` — the core/ring color, used deliberately (CTAs, active nav, focus rings), never scattered |
| Secondary | Lavender — the lighter orbit ring; reused as `--gradient-accent` for marketing gradients only |
| Accent | Soft Rose (`--accent-rose`) — the blush ring color; sparing use (badges, decorative), never a primary action color |
| Neutrals | Warm off-white / blush-beige (light mode), warm purple-charcoal (dark mode) — never a clinical white or neutral gray |
| Typography | Manrope (the logo's own typeface) for Latin; Cairo for Arabic — a professional geometric pairing, not a bolted-on fallback |
| Shape language | Circular/orbital, soft. Buttons, badges, and single-line inputs are **fully pill-shaped** (`rounded-full`); cards and textareas use a large, soft radius |
| Shadow language | Soft, diffused, **purple-tinted** (`--shadow-color`) — never neutral gray |
| Motion language | Orbital — gentle float/rotation; a new `orbit-spin-slow` keyframe exists for the `Logo` mark itself (opt-in via an `animated` prop, off by default so it doesn't distract in a persistent nav) |
| Personality | Warm, optimistic, soft-premium — a genuine shift from the earlier session's colder, Linear-inspired dark-violet system, which is why tokens were rebuilt rather than patched |

**Color tokens, WCAG-verified, not assumed:** every text/background pair in both dark and light was checked programmatically (relative luminance → contrast ratio) against WCAG AA (4.5:1 for text, 3:1 for non-text like the focus ring). Three real failures were found this way and fixed: dark-mode `--primary` at its initial lightness only produced 3.71:1 with white button text (lowered until 5.27:1); dark-mode `--destructive` similarly only hit 3.82:1 (lowered to 4.89:1); light-mode `--success` and `--warning` both failed with white text (28% → 5.89:1, 32% → 5.66:1). Every other pair passed on the first check. This is why the exact lightness values in `app/globals.css` look oddly specific — they're the smallest change that cleared 4.5:1, not round numbers.

A new `Logo` component (`components/logo.tsx`) — inline SVG, no image asset — replaces both the placeholder Sparkles-icon mark from the prior session and matches the official reference exactly (dual rings, rose secondary, satellite dots).

## Language System (English / Arabic, new this session)

Full bilingual infrastructure — English (LTR, default) and Arabic (full RTL) — built as a lightweight custom context rather than a routing-based i18n library (`next-intl`, etc.), specifically to avoid restructuring every route behind a `/en/`/`/ar/` URL prefix, which would have touched `middleware.ts`, Clerk's own routes, and every existing link in the app for no benefit this product needs.

- **`lib/i18n/config.ts`** — locale list, RTL-locale set, cookie name.
- **`lib/i18n/messages/{en,ar}.json`** — the dictionaries. Every string is real, professionally-written Arabic (not machine-translated filler) — nav labels, all marketing copy, Dashboard, FAQ, testimonials, everything covered so far.
- **`lib/i18n/locale-provider.tsx`** — `LocaleProvider` (Context) + `useTranslations()` hook returning `{ locale, dir, setLocale, t }`. `t("dot.path.key")` looks up the dictionary, falling back to English then the raw key if a translation is ever missing (never a blank string or a crash).
- **No flash of the wrong direction**: unlike `next-themes`' client-side script-injection approach (necessary there because theme preference might only exist in `localStorage`), locale is decided **server-side** in `app/layout.tsx` by reading a `NEXT_LOCALE` cookie via `next/headers` — `<html lang dir>` is correct on the very first byte sent. `generateMetadata` independently reads the same cookie so even the `<title>` is locale-correct on first response (verified: `curl -b "NEXT_LOCALE=ar"` returns an Arabic `<title>` with no client-side correction needed).
- **`LanguageToggle`** (`components/language-toggle.tsx`) — in `MarketingNav`, the product `Topbar`, **and** inserted into the existing (not yet redesigned) `/settings` page as a small standalone card — satisfying "available in navigation and inside Settings" without redesigning the rest of that page.
- **RTL correctness**: physical-direction Tailwind utilities (`left-*`, `right-*`, `pl-*`/`pr-*`, `border-l`/`border-r`, `ml-*`/`mr-*`) were converted to logical properties (`start-*`/`end-*`, `ps-*`/`pe-*`, `border-s`/`border-e`, `ms-*`/`me-*`) throughout the Sidebar, marketing nav/sections, and shared Radix primitives (`dropdown-menu.tsx`, `dialog.tsx`, `accordion.tsx`) — these flip automatically via the browser once `dir="rtl"` is set, no per-component RTL variant needed. The two things logical properties *can't* cover — the Sidebar's mobile-drawer slide transform, and directional arrow icons (`ArrowRight`) — get an explicit `rtl:` Tailwind variant override instead (`rtl:translate-x-full`, `rtl:rotate-180`). Flexbox row-direction layouts needed no changes at all: `flex-direction: row` is itself a logical (inline-direction) property per the CSS spec, so it already flows RTL automatically.
- **Coverage so far**: the marketing site (all sections), the App Shell (Sidebar/Topbar/UserMenu/ThemeToggle), Dashboard, Skill-Gap Analysis, Roadmap, CV Feedback, and Notifications are fully translated and RTL-correct. Onboarding, Profile, and the rest of Settings remain English-only pending their own redesign pass — consistent with the brand direction's own explicit sequencing ("first establish the design system, then migrate every page").
- **Notifications' relative timestamps use native `Intl.RelativeTimeFormat`/`Intl.DateTimeFormat`, not translation-dictionary strings.** "5 minutes ago" / "قبل 5 دقائق" needs correct plural/dual agreement in Arabic that a hand-written dictionary entry can't cleanly express; the native `Intl` APIs handle that (and locale-correct digit/date formatting) for free, keyed off the same `Locale` ("en"/"ar") already used everywhere else. Zero new dependency, zero new translation keys for time — copy this approach for any future page that needs relative time.
- **`t()` gained `{{var}}` interpolation** (Skill-Gap Analysis session) — needed the moment a translated string had to embed a number (`common.version`: "Version {{n}}" / "الإصدار {{n}}"); `t(key, { n: 3 })` replaces `{{n}}` in the resolved string, and now also handles multiple variables at once (Roadmap's `roadmap.progress`: "{{completed}} of {{total}} steps complete"). Infrastructure completion, not a new pattern — every future page with a count/version/date in a translated string reuses this rather than falling back to string concatenation (which breaks Arabic word order).
- **`ConfidenceBadge` is now `"use client"` and translation-aware** (Skill-Gap Analysis session) — it previously hardcoded the English word "confidence" and the level name directly in JSX. Since it's shared across Dashboard, Skill-Gap Analysis, Roadmap, and the marketing Product Preview mockup, the fix was made once in the shared component rather than duplicated per call site; new `common.confidence`/`confidenceHigh`/`confidenceMedium`/`confidenceLow` keys back it. Safe to render from a Server Component parent — Server Components may render Client Components as children.
- **`ExplainButton` is now translation-aware too** (Roadmap session — a gap found while reusing it here: it had been dropped into Skill-Gap Analysis's already-shipped, fully-translated page with its own internal strings — "Why?", "Explaining…", "Grounded in:" — still hardcoded in English). Fixed once in the shared component (`common.why`/`hideExplanation`/`explaining`/`explainError`, plus reusing `common.retry`/`common.groundedIn`); this silently fixes the same latent gap on the already-shipped Skill-Gap Analysis page too, not only Roadmap. Also switched its one physical-direction class (`border-l-2`, `-ml-2`) to logical (`border-s-2`, `-ms-2`) while in the file.
- **`dashboard.retry` promoted to `common.retry`**, and **`skillGapAnalysis.version`/`completeOnboarding`/`groundedIn` promoted to `common.version`/`completeOnboarding`/`groundedIn`** (this session) — each of these turned out to be needed again verbatim by Roadmap (version badge, empty-state CTA, and — via `ExplainButton` — grounded-in text), confirming they were genuinely shared concepts rather than page-specific copy. Reuse the `common.*` key for any future page that needs the same thing rather than adding a per-page duplicate.
- **`Toaster` (`components/ui/sonner.tsx`) got its first real caller** (Skill-Gap Analysis's Refresh action) and, in the process, its position ("bottom-right") turned out to be hardcoded and RTL-blind — fixed to flip to "bottom-left" when `dir === "rtl"` via `useTranslations()`. Roadmap and CV Feedback are its second and third callers (status-change and submit/delete outcomes), confirming the fix generalizes.
- **`components/ui/progress.tsx` (Radix `Progress`) got its first real caller** (Roadmap's completion bar) — it existed since the original design-system build-out but had never actually been wired into a page until now.
- **`components/ui/dialog.tsx` (Radix `Dialog`) got its first real caller** (CV Feedback session) — same story as `Progress`: built during the original design-system pass, never actually used until now, this time replacing a native `window.confirm()` for round deletion with a themed, accessible confirmation modal (focus trap and Escape-to-close come from Radix, not hand-rolled).
- **A three-page-old error-parsing helper was promoted out of duplication** (CV Feedback session): Skill-Gap Analysis and Roadmap had each grown their own identical local `extractErrorMessage()` (to pull a clean message out of FastAPI's `{"detail": ...}` JSON body, since `apiFetch` only returns raw response text). CV Feedback needed the exact same thing a third time — at that point it was genuinely shared code, not page-specific, so it moved to `lib/api.ts` as `extractApiErrorMessage()` and both existing call sites were updated to import it instead of keeping their own copies.
- **`components/ui/tooltip.tsx` (Radix `Tooltip`) got its first real caller** (Notifications session) — `TooltipProvider` has wrapped the whole app since the original design-system pass, but no page had actually rendered a `Tooltip` until Notifications' icon-only "mark as read" button needed one (still paired with a real `aria-label`, not relying on the tooltip alone for accessibility).

## Design System (2026-08 — architecture from the original redesign; token *values* since superseded by the Official Logo System above)

The entire visual language was rebuilt from scratch — dark-mode-first, a six-step type scale, and a persistent app shell (sidebar + topbar) replacing the old "every page is its own centered card" layout. **No backend, API, database, business-rule, or authentication-logic change was made anywhere in this pass** — every existing `fetch` call, redirect, and validation rule is byte-identical to before; only how it's rendered changed. Full rationale and before/after reasoning for each redesigned page: [`docs/99-Audits/PHASE0_EXECUTION_PLAN.md`](../docs/99-Audits/PHASE0_EXECUTION_PLAN.md) is the *feature* roadmap; this redesign is tracked separately in `CHANGELOG.md` since it's presentation-only and doesn't move the Phase 0 completion percentage.

- **Tokens** (`app/globals.css`, `tailwind.config.ts`): `:root` is the dark palette (the product default); `[data-theme="light"]` overrides it — the inverse of the previous shadcn-default setup, deliberately, per "dark mode first." Semantic tokens: `surface`/`surface-hover` (card backgrounds, distinct from `background`), `sidebar`/`sidebar-active`, `accent`, `accent-rose`, `success`/`warning`/`destructive`, `border-subtle`. A six-step type scale (`hero`/`display`/`title`/`heading`/`body`/`small`/`caption`) replaces ad hoc `text-sm`/`text-lg` usage. A cool-purple-tinted, multi-stop `boxShadow` scale replaces Tailwind's neutral-black default. `tailwindcss-animate` plus custom keyframes (`fade-in`, `slide-up`, `shimmer`, `float`, `orbit-spin`, `accordion-down`/`up`) power all motion — no Framer Motion or other animation runtime was added. Exact color *values* now come from the logo (see "Official Logo System" above) rather than the invented indigo/violet this section originally described.
- **Font**: Manrope (Latin) + Cairo (Arabic) — see "Official Logo System" and "Language System" above for why and how they switch. JetBrains Mono remains available for anything monospace-appropriate.
- **New primitives** (`components/ui/`): `skeleton.tsx` (shimmer, replaces every page's hand-duplicated `animate-pulse` div), `dialog.tsx`, `dropdown-menu.tsx`, `tooltip.tsx`, `avatar.tsx`, `separator.tsx`, `progress.tsx`, `sonner.tsx` (toast host), `accordion.tsx` (FAQ) — all thin Radix-primitive wrappers (`@radix-ui/react-*`) themed to the token system, accessible (keyboard nav, focus trapping, ARIA) by construction, and RTL-correct (logical properties, not physical `left`/`right`).
- **Redesigned primitives**: `button.tsx` (pill-shaped/`rounded-full` per the logo's UI reference; `secondary`/`link` variants; an `isLoading` prop with a built-in spinner; a 150ms press/hover transition), `card.tsx`, `input.tsx` (pill-shaped)/`textarea.tsx` (soft large radius) with consistent focus-ring + `aria-invalid` styling, `label.tsx`, `badge.tsx` (pill-shaped; takes a `variant` prop — `success`/`warning`/`destructive`/`primary`/`outline`/`rose` — instead of every call site hand-writing its own color classes).
- **App Shell** (`components/shell/`): a persistent `Sidebar` (icon + label nav, active-route highlighting, a mobile off-canvas drawer with Escape-to-close, RTL-safe) and `Topbar` (page title derived from the current route, a `ThemeToggle`, a `LanguageToggle`, and a `UserMenu` that reads Clerk's own `useUser()`/`useClerk()` hooks directly — no auth logic added, only a themed presentation over hooks Clerk already provides). Wired via a new `app/(app)/layout.tsx` route group, which changes no URLs — `(app)` is a file-organization convention Next.js strips from the path.
- **`ConfidenceBadge`/`ExplainButton`**: redesigned to use the new `Badge` variants and `Skeleton`/`isLoading`; `ExplainButton` now also renders `grounded_on` (the backend has always returned it; the previous version silently discarded it — a presentation-only fix, same endpoint, same response shape).

### A Suspense/redirect gotcha (worth knowing before redesigning the next page)

Adding a route-level `loading.tsx` to `/dashboard` was tried first and reverted: Next.js wraps the entire route in a Suspense boundary when `loading.tsx` exists for that segment, which starts streaming a `200` response immediately — and once *any* content has streamed, a later `redirect()` call inside the page can no longer send a real HTTP `3xx`, so Next.js silently falls back to a slower client-side `<meta http-equiv="refresh">` redirect instead. This was caught by comparing `curl -D -` output against an unmodified page (`/skill-gap-analysis`) before and after, not by inspection alone. **Fix:** no route-level `loading.tsx` on any page that also does a server-side auth/onboarding redirect (which is every top-level authenticated page) — instead wrap only the data-fetching portion in an inline `<Suspense>` *inside* the page component, after the redirect checks have already resolved. See `app/(app)/dashboard/page.tsx` for the pattern to copy on every subsequent page redesign. **Related, this session:** translated text inside that Suspense boundary needs `useTranslations()`, which requires a Client Component — since the Server Component that fetches data can't also be the one rendering hooks-dependent JSX, the render half was split out into a sibling `dashboard-view.tsx` (`"use client"`) that receives the already-fetched data as props. Copy this split, not a single file, when translating the next Suspense-wrapped page.

## Notifications (2026-08 — fourth product page migrated)

Reframed from an inbox-style list into an activity timeline, grounded in exactly what `GET /notifications` (`backend/app/api/routers/notifications.py`) actually returns — `id`, `category`, `message`, `is_read`, `created_at`, nothing else. Several judgment calls here are worth being explicit about, since the brief's requested taxonomy and bulk action don't map 1:1 onto the real backend:

- **Only three notification categories are real.** `backend/app/schemas/settings.py`'s `NOTIFICATION_CATEGORIES` is the backend's own authoritative, complete list — `analysis_complete`, `roadmap_updated`, `cv_feedback_complete` — confirmed by grepping every `notify(...)` call site in the codebase (`app/api/routers/ai_career_center.py`, three call sites, no others exist). The requested seven-type taxonomy (AI Insight / Recommendation / Reminder / Progress Update / Roadmap Update / Goal Update / System Message) doesn't exist in the data as seven live categories. The three real ones were mapped onto the closest accurate match — `analysis_complete` → "AI Insight" (`Sparkles`, primary), `roadmap_updated` → "Roadmap Update" (`Route`, rose), `cv_feedback_complete` → "Recommendation" (`FileText`, success) — and the full seven-entry icon/color/label lookup table was still built in `notifications-view.tsx`, so a future backend category (a real "Reminder" or "Goal Update" trigger, say) picks up a visual treatment automatically with zero frontend change. But nothing today ever populates those other four; no notification of those types was fabricated to "fill out" the design. An unrecognized category string (defensive case, not a real one) falls back to the generic "System Message" treatment (`Bell`, outline) rather than crashing or showing a raw string.
- **No "mark all as read" was built.** The backend has exactly one mutation, `PATCH /notifications/{id}/read`, scoped to a single notification — there is no bulk endpoint. Looping N individual requests behind one button was considered and deliberately rejected: it would present a non-atomic, partial-failure-prone client-side composition as if it were one clean server action (what happens if request 7 of 12 fails? silently ignore it? show a confusing partial-success toast?), which is a worse, less honest experience than not having the button. This is a real, documented gap — a `PATCH /notifications/read-all` (or similar) endpoint would be a small, reasonable backend addition if this is wanted; the frontend didn't manufacture a workaround for it.
- **Grouping (Today/Yesterday/Earlier) and relative timestamps are computed entirely client-side** from the `created_at` the backend already returns — no new endpoint, no new field. See the Language System section above for why the timestamp formatting itself uses native `Intl` APIs rather than translated strings.
- **A pre-existing backend inconsistency, noted but not touched** (out of scope — "keep backend logic unchanged"): both notification endpoints return bare `dict`/`list[dict]` with no Pydantic `response_model`, the only two endpoints in the entire API that don't — everything else (`ai_career_center.py`, `settings.py`, `profiles.py`) uses a typed `XRead` schema consistently, which is also why `NotificationRead` on the frontend types `category` as a plain `string` rather than a literal union. Worth a small backend follow-up (`response_model=list[NotificationRead]` with a Pydantic schema) for OpenAPI/Swagger completeness, independent of anything in this redesign pass.

## Onboarding flow (implemented)

`sign-in`/`sign-up` → `dashboard` (checks `GET /profile/onboarding-status`; redirects to `/onboarding` if incomplete) → `onboarding` wizard (Profile → Goal → Skills, each persisted immediately via its own API call, not batched) → generates the first Skill-Gap Analysis and its cascaded Roadmap → back to `dashboard`, now fully unlocked, with links to `/skill-gap-analysis`, `/roadmap`, `/cv-feedback`, `/notifications`, `/profile`, and `/settings`.

## Accessibility pattern (`/cv-feedback`, `/profile`, `/settings` are the reference implementations)

Established prior to the design-system work, not yet retrofitted everywhere (see Known gaps): every form input has an explicit `<label htmlFor>`/`id` pair; validation errors are wired to their input via `aria-invalid`/`aria-describedby`; a visually-hidden (`sr-only`) `aria-live="polite"` region announces async status changes (submitting, success, failure) to assistive technology without requiring a sighted scan of the page; focus is moved programmatically to newly-appeared result content after an action completes (a `ref` + `tabIndex={-1}` + `.focus()`, not just a visual scroll); collapsible content uses native `<details>`/`<summary>` rather than a custom expand/collapse widget, since the native element is keyboard-operable and screen-reader-announced with zero ARIA authoring required; destructive actions get an explicit confirmation step; toggle-style controls (notification-category mutes) expose their state via `aria-pressed` rather than color alone. **Now migrated (CV Feedback session)**: round deletion's confirmation step moved from a bare `window.confirm()` to a themed, Radix-backed `Dialog` — still an explicit confirmation step, just no longer an unstyled native browser dialog; account deletion (`/settings`, irreversible and higher-stakes than a single CV round, not yet migrated) keeps its stronger type-to-confirm-your-own-email step, which remains the right call for that specific action's stakes.

## Known gaps (full tracking in [`PHASE0-AUDIT.md`](../PHASE0-AUDIT.md) and [`docs/99-Audits/`](../docs/99-Audits/) at the repo root)

- **Product redesign/translation is five pages deep; marketing site is done.** The public marketing site (`/`, `/privacy`, `/terms`) is fully redesigned, themed, and bilingual. Inside the product, Dashboard, Skill-Gap Analysis, Roadmap, CV Feedback, and Notifications have been moved into the new App Shell / design system / language system — Onboarding, Profile, and Settings (aside from its new Language card) all still render pre-redesign, English-only UI until each gets its own pass. Sign-in/Sign-up are Clerk-hosted and inherit the new tokens/font automatically but haven't had a structural redesign (Clerk's own UI has limited restyling surface) or translation (Clerk's hosted components have their own separate localization mechanism, not wired to this app's `lib/i18n`).
- **Skill-Gap Analysis's history view is still unbuilt.** The backend's `GET /skill-gap-analysis/history` endpoint exists and is untouched, but this pass only wired the `refresh` action (needed to give the page any way to trigger a new analysis at all — it previously had none). Showing what changed between versions (FR-AICC-6/BR-PROG-1) is bundled with the Progress screen below, not solved piecemeal per page.
- **Roadmap needed no new backend wiring** — unlike Skill-Gap Analysis, the pre-redesign Roadmap page already called every available roadmap endpoint (`current`, item `status` PATCH, item `explain`); there is no manual roadmap-refresh endpoint to expose (a Roadmap only regenerates as an automatic cascade of a Skill-Gap Analysis refresh, per `_generate_roadmap` in `ai_career_center.py`), so this pass is presentation-only for this page, plus the `ExplainButton`/`ConfidenceBadge`/`Toaster` shared-component fixes noted above.
- **CV Feedback's "strengths vs improvement areas" was honestly reinterpreted, not fabricated.** The requested grouping doesn't map onto what the backend actually produces: `CVFeedbackAgent` (`ai/careeros_ai/agents/cv_feedback.py`) is explicitly a critique-only capability — its system prompt says "Do not rewrite the document — critique only what was submitted" — and its only category axis is `factual_structural` vs `judgment_call` (objective/clear-cut issues vs subjective/debatable ones), never a positive "strength" category. Inventing a strengths section would mean showing the user AI-generated praise the agent never actually produced, which this project's whole RAI stance (grounded, never fabricated, "never a black box") rules out. The real category split was implemented instead — two labeled, visually distinct groups with their own icon and badge color — which is what the request was reaching for, just under a different, more accurate name. If a genuine strengths/positives capability is wanted, that's a backend/agent change (new category, new prompt instruction), not a frontend relabeling.
- **CV Feedback's `relevance_to_goal` field was exposed for the first time.** `CVFeedbackItemRead.relevance_to_goal` has always been returned by `POST/GET /cv-feedback` — the backend explains, per item, why that piece of feedback matters for the user's specific target role — but the pre-redesign page never rendered it. Now shown as a labeled callout under each feedback item ("Why this matters for your goal"), reusing the same visual treatment `ExplainButton`'s revealed answer already uses.
- **CV Feedback's "no active goal" 400 (`BR-AICC-14`) now gets a real affordance.** Submitting without an active goal (reachable in practice — Settings supports deactivating/reactivating a goal) previously surfaced as a plain red error string. It now gets its own inline callout with a direct link to `/profile` to set a goal, detected by pattern-matching the extracted error message rather than a new backend error code — a pragmatic, bounded technique, not a new app-wide error-classification system.
- **Notifications has no bulk "mark all as read."** The backend has no bulk endpoint (only a single-notification `PATCH .../read`), and this pass deliberately didn't fake one by looping requests client-side — see the dedicated Notifications section above for the full reasoning. A small backend addition (`PATCH /notifications/read-all` or similar) would unblock a real implementation.
- **Notifications' category taxonomy is only ⅜ populated with real data.** Four of the seven visual categories the UI supports (Reminder, Progress Update, Goal Update, System Message) have no backend trigger that ever produces them today — only `analysis_complete`/`roadmap_updated`/`cv_feedback_complete` are live. The lookup tables exist so a future backend category "just works," not to imply those types already occur.
- **A pre-existing backend inconsistency was found, not fixed** (out of scope for a presentation-only pass): the two notification endpoints are the only ones in the whole API without a Pydantic `response_model`, unlike every other router. Noted in the Notifications section above as a small independent backend follow-up.
- Progress/history screen doesn't exist (no backend endpoint for a dedicated Progress view yet either) — unrelated to this redesign, tracked in `docs/99-Audits/PHASE0_EXECUTION_PLAN.md` M8.
- Error boundary / `loading.tsx` conventions: Dashboard, Skill-Gap Analysis, Roadmap, CV Feedback, and Notifications have a real (inline-Suspense) loading state and a retry action on their error state. Profile and Settings already had a retry action from prior work; Onboarding still has none.
- Accessibility has been addressed on `/cv-feedback` and `/notifications` (now migrated — see above), `/profile`, `/settings` (established pattern). Landing/Dashboard/Skill-Gap Analysis/Roadmap/CV Feedback/Notifications inherit the new focus-visible/ARIA-conscious primitives; severity, confidence, roadmap status, and notification category are all shown with a colored indicator *and* a text label, never color alone. Roadmap's status control and expandable-details toggle, CV Feedback's round deletion dialog, and Notifications' mark-as-read tooltip button are all fully keyboard-operable (Radix `DropdownMenu`/`Dialog`/`Tooltip`, native `<details>`) with no custom ARIA authored.
