## Official Logo System (2026-08 — supersedes the earlier improvised palette/font)

The user supplied Orbit's official logo and brand board; the entire token system below was re-derived from it, replacing the earlier session's invented indigo/Inter system. **Brand analysis:**

| Aspect | Reading |
|---|---|
| Mark | Two intersecting orbit rings (royal purple primary, soft rose secondary) around a purple core, with satellite dots at the ring intersections — literally depicts the name |
| Primary | Royal Purple, `hsl(262 …)` — the core/ring color, used deliberately (CTAs, active nav, focus rings), never scattered |
| Secondary | Lavender — the lighter orbit ring; reused as `--gradient-accent` for marketing gradients only |
| Accent | Soft Rose (`--accent-rose`) — the blush ring color; sparing use (badges, decorative), never a primary action color |
| Neutrals | Warm off-white / blush-beige (light mode), warm purple-charcoal (dark mode) — never a clinical white or neutral gray |
| Typography | Manrope (the logo's own typeface) for Latin; Cairo for Arabic — a professional geometric pairing, not a bolted-on fallback |
| Shape language | Circular/orbital, soft. Buttons, badges, and single-line inputs are **fully pill-shaped** (`rounded-full`); cards and textareas use a large, soft radius |
| Shadow language | Soft, diffused, **purple-tinted** (`--shadow-color`) — never neutral gray |
| Motion language | Orbital — gentle float/rotation; a new `orbit-spin-slow` keyframe exists for the `Logo` mark itself (opt-in via an `animated` prop, off by default so it doesn't distract in a persistent nav) |
| Personality | Warm, optimistic, soft-premium — a genuine shift from the earlier session's colder, Linear-inspired dark-violet system, which is why tokens were rebuilt rather than patched |

**Color tokens, WCAG-verified, not assumed:** every text/background pair in both dark and light was checked programmatically (relative luminance → contrast ratio) against WCAG AA (4.5:1 for text, 3:1 for non-text like the focus ring). Three real failures were found this way and fixed: dark-mode `--primary` at its initial lightness only produced 3.71:1 with white button text (lowered until 5.27:1); dark-mode `--destructive` similarly only hit 3.82:1 (lowered to 4.89:1); light-mode `--success` and `--warning` both failed with white text (28% → 5.89:1, 32% → 5.66:1). Every other pair passed on the first check. This is why the exact lightness values in `app/globals.css` look oddly specific — they're the smallest change that cleared 4.5:1, not round numbers.

A new `Logo` component (`components/logo.tsx`) — inline SVG, no image asset — replaces both the placeholder Sparkles-icon mark from the prior session and matches the official reference exactly (dual rings, rose secondary, satellite dots).

## Language System (English / Arabic, new this session)

Full bilingual infrastructure — English (LTR, default) and Arabic (full RTL) — built as a lightweight custom context rather than a routing-based i18n library (`next-intl`, etc.), specifically to avoid restructuring every route behind a `/en/`/`/ar/` URL prefix, which would have touched `middleware.ts`, Clerk's own routes, and every existing link in the app for no benefit this product needs.

- **`lib/i18n/config.ts`** — locale list, RTL-locale set, cookie name.
- **`lib/i18n/messages/{en,ar}.json`** — the dictionaries. Every string is real, professionally-written Arabic (not machine-translated filler) — nav labels, all marketing copy, Dashboard, FAQ, testimonials, everything covered so far.
- **`lib/i18n/locale-provider.tsx`** — `LocaleProvider` (Context) + `useTranslations()` hook returning `{ locale, dir, setLocale, t }`. `t("dot.path.key")` looks up the dictionary, falling back to English then the raw key if a translation is ever missing (never a blank string or a crash).
- **No flash of the wrong direction**: unlike `next-themes`' client-side script-injection approach (necessary there because theme preference might only exist in `localStorage`), locale is decided **server-side** in `app/layout.tsx` by reading a `NEXT_LOCALE` cookie via `next/headers` — `<html lang dir>` is correct on the very first byte sent. `generateMetadata` independently reads the same cookie so even the `<title>` is locale-correct on first response (verified: `curl -b "NEXT_LOCALE=ar"` returns an Arabic `<title>` with no client-side correction needed).
- **`LanguageToggle`** (`components/language-toggle.tsx`) — in `MarketingNav`, the product `Topbar`, **and** inserted into the existing (not yet redesigned) `/settings` page as a small standalone card — satisfying "available in navigation and inside Settings" without redesigning the rest of that page.
- **RTL correctness**: physical-direction Tailwind utilities (`left-*`, `right-*`, `pl-*`/`pr-*`, `border-l`/`border-r`, `ml-*`/`mr-*`) were converted to logical properties (`start-*`/`end-*`, `ps-*`/`pe-*`, `border-s`/`border-e`, `ms-*`/`me-*`) throughout the Sidebar, marketing nav/sections, and shared Radix primitives (`dropdown-menu.tsx`, `dialog.tsx`, `accordion.tsx`) — these flip automatically via the browser once `dir="rtl"` is set, no per-component RTL variant needed. The two things logical properties *can't* cover — the Sidebar's mobile-drawer slide transform, and directional arrow icons (`ArrowRight`) — get an explicit `rtl:` Tailwind variant override instead (`rtl:translate-x-full`, `rtl:rotate-180`). Flexbox row-direction layouts needed no changes at all: `flex-direction: row` is itself a logical (inline-direction) property per the CSS spec, so it already flows RTL automatically.
- **Coverage so far**: the marketing site (all sections), the App Shell (Sidebar/Topbar/UserMenu/ThemeToggle), Dashboard, Skill-Gap Analysis, Roadmap, CV Feedback, Notifications, Settings, and now Progress (a brand-new page, translated from the start — not a migration) are fully translated and RTL-correct. Only Onboarding and Profile remain English-only pending their own redesign pass — consistent with the brand direction's own explicit sequencing ("first establish the design system, then migrate every page").
- **Notifications' relative timestamps use native `Intl.RelativeTimeFormat`/`Intl.DateTimeFormat`, not translation-dictionary strings.** "5 minutes ago" / "قبل 5 دقائق" needs correct plural/dual agreement in Arabic that a hand-written dictionary entry can't cleanly express; the native `Intl` APIs handle that (and locale-correct digit/date formatting) for free, keyed off the same `Locale` ("en"/"ar") already used everywhere else. Zero new dependency, zero new translation keys for time — copy this approach for any future page that needs relative time.
- **`t()` gained `{{var}}` interpolation** (Skill-Gap Analysis session) — needed the moment a translated string had to embed a number (`common.version`: "Version {{n}}" / "الإصدار {{n}}"); `t(key, { n: 3 })` replaces `{{n}}` in the resolved string, and now also handles multiple variables at once (Roadmap's `roadmap.progress`: "{{completed}} of {{total}} steps complete"). Infrastructure completion, not a new pattern — every future page with a count/version/date in a translated string reuses this rather than falling back to string concatenation (which breaks Arabic word order).
- **`ConfidenceBadge` is now `"use client"` and translation-aware** (Skill-Gap Analysis session) — it previously hardcoded the English word "confidence" and the level name directly in JSX. Since it's shared across Dashboard, Skill-Gap Analysis, Roadmap, and the marketing Product Preview mockup, the fix was made once in the shared component rather than duplicated per call site; new `common.confidence`/`confidenceHigh`/`confidenceMedium`/`confidenceLow` keys back it. Also switched its one physical-direction class (`border-l-2`, `-ml-2`) to logical (`border-s-2`, `-ms-2`) while in the file.

### A Suspense/redirect gotcha (worth knowing before redesigning the next page)

Adding a route-level `loading.tsx` to `/dashboard` was tried first and reverted: Next.js wraps the entire route in a Suspense boundary when `loading.tsx` exists for that segment, which starts streaming a `200` response immediately — and once *any* content has streamed, a later `redirect()` call inside the page can no longer send a real HTTP `3xx`, so Next.js silently falls back to a slower client-side `<meta http-equiv="refresh">` redirect instead. This was caught by comparing `curl -D -` output against an unmodified page (`/skill-gap-analysis`) before and after, not by inspection alone. **Fix:** no route-level `loading.tsx` on any page that also does a server-side auth/onboarding redirect (which is every top-level authenticated page) — instead wrap only the data-fetching portion in an inline `<Suspense>` *inside* the page component, after the redirect checks have already resolved. See `app/(app)/dashboard/page.tsx` for the pattern to copy on every subsequent page redesign. **Related, this session:** translated text inside that Suspense boundary needs `useTranslations()`, which requires a Client Component — since the Server Component that fetches data can't also be the one rendering hooks-dependent JSX, the render half was split out into a sibling `dashboard-view.tsx` (`"use client"`) that receives the already-fetched data as props. Copy this split, not a single file, when translating the next Suspense-wrapped page.

## Notifications (2026-08 — fourth product page migrated)

Reframed from an inbox-style list into an activity timeline, grounded in exactly what `GET /notifications` (`backend/app/api/routers/notifications.py`) actually returns — `id`, `category`, `message`, `is_read`, `created_at`, nothing else. Several judgment calls here are worth being explicit about, since the brief's requested taxonomy and bulk action don't map 1:1 onto the real backend:

- **Only three notification categories are real.** `backend/app/schemas/settings.py`'s `NOTIFICATION_CATEGORIES` is the backend's own authoritative, complete list — `analysis_complete`, `roadmap_updated`, `cv_feedback_complete` — confirmed by grepping every `notify(...)` call site in the codebase (`app/api/routers/ai_career_center.py`, three call sites, no others exist). The requested seven-type taxonomy (AI Insight / Recommendation / Reminder / Progress Update / Roadmap Update / Goal Update / System Message) doesn't exist in the data as seven live categories. The three real ones were mapped onto the closest accurate match — `analysis_complete` → "AI Insight" (`Sparkles`, primary), `roadmap_updated` → "Roadmap Update" (`Route`, rose), `cv_feedback_complete` → "Recommendation" (`FileText`, success) — and the full seven-entry icon/color/label lookup table was still built in `notifications-view.tsx`, so a future backend category (a real "Reminder" or "Goal Update" trigger, say) picks up a visual treatment automatically with zero frontend change. But nothing today ever populates those other four; no notification of those types was fabricated to "fill out" the design. An unrecognized category string (defensive case, not a real one) falls back to the generic "System Message" treatment (`Bell`, outline) rather than crashing or showing a raw string.
- **No "mark all as read" was built.** The backend has exactly one mutation, `PATCH /notifications/{id}/read`, scoped to a single notification — there is no bulk endpoint. Looping N individual requests behind one button was considered and deliberately rejected: it would present a non-atomic, partial-failure-prone client-side composition as if it were one clean server action (what happens if request 7 of 12 fails? silently ignore it? show a confusing partial-success toast?), which is a worse, less honest experience than not having the button. This is a real, documented gap — a `PATCH /notifications/read-all` (or similar) endpoint would be a small, reasonable backend addition if this is wanted; the frontend didn't manufacture a workaround for it.
- **Grouping (Today/Yesterday/Earlier) and relative timestamps are computed entirely client-side** from the `created_at` the backend already returns — no new endpoint, no new field. See the Language System section above for why the timestamp formatting itself uses native `Intl` APIs rather than translated strings.
- **A pre-existing backend inconsistency, noted but not touched** (out of scope — "keep backend logic unchanged"): both notification endpoints return bare `dict`/`list[dict]` with no Pydantic `response_model`, the only two endpoints in the entire API that don't — everything else (`ai_career_center.py`, `settings.py`, `profiles.py`) uses a typed `XRead` schema consistently, which is also why `NotificationRead` on the frontend types `category` as a plain `string` rather than a literal union. Worth a small backend follow-up (`response_model=list[NotificationRead]` with a Pydantic schema) for OpenAPI/Swagger completeness, independent of anything in this redesign pass.

## Settings (2026-08 — fifth product page migrated, the widest one so far)

Reframed from a single scrolling form into eight clearly separated cards — Profile & Goal, Account, Subscription & Billing, Notification Preferences, Preferences (Theme + Language), Privacy & Data, Security, and a Danger Zone — one per real backend concern, not one giant `<form>`. Every card's data comes from its own backend call, fetched in parallel server-side (`Promise.all` in `settings/page.tsx`) and caught independently, so (for example) a `/settings/subscription` failure shows a small inline error only inside that one card, with the rest of the page fully usable — a real, meaningful upgrade over the old page's identical-but-less-visible per-section loading pattern.

- **Profile & Goal is new** — a read-only summary card (background/education/experience previews, up to 6 skill badges, the active goal) built from `GET /profile` and `GET /profile/goals/active`, with a "Edit profile & goal" link to the still-not-yet-migrated `/profile` page. This isn't duplicated business logic — it's two more read-only `GET`s powering a summary, not a second copy of `/profile`'s edit form — and it's what makes "Profile" a real, visible section of Settings per the brief without redesigning `/profile` itself, which stayed explicitly out of scope for this pass.
- **Theme is now controllable from Settings, not only the Topbar/marketing nav.** A new "Preferences" card holds both Theme (Light/Dark/System, via the same `next-themes` `useTheme()` hook `ThemeToggle` already uses) and Language (English/العربية) as two rows in one card rather than two near-duplicate cards — closes a real gap in the original Theme System brief ("switch anywhere in the application"), which had only ever been satisfied for Language, not Theme, in Settings specifically.
- **Security is new** — previously nonexistent as a concept on this page. There is no password/2FA/session-list backend in this stack (Clerk owns authentication entirely, and no such endpoints exist in `backend/app/api/routers/`) — the card says exactly that (auth is managed by Clerk) rather than implying controls that don't exist, plus a real "Sign out of this device" action using Clerk's own `useClerk().signOut()`, already used elsewhere in the app (`UserMenu`).
- **A real, previously-uncaught bug fixed along the way**: the old page's subscription-status and goal-active badges used hardcoded Tailwind color classes (`bg-emerald-100 text-emerald-900 dark:bg-emerald-950 dark:text-emerald-200`) instead of the design-system's own `Badge` `variant` prop — meaning they silently bypassed the WCAG-verified token system entirely. Fixed on `/settings` (now `variant="success"`); **the identical bug still exists on `/profile`'s "Active" goal badge**, untouched here since that page is out of scope for this pass — flagged so it isn't lost track of before `/profile`'s own migration.
- **`window.confirm()` → `Dialog` for "clear profile data"**, matching the precedent CV Feedback set for round deletion — `Dialog`'s second real caller. **Account deletion deliberately did not get the same treatment** — it keeps its stronger type-your-own-email-to-confirm inline flow (just restyled with current tokens), since that extra friction is the intentionally correct choice for the one truly irreversible, highest-stakes action on this page; downgrading it to a one-click `Dialog` would be a regression, not an improvement.
- **`Separator` (`components/ui/separator.tsx`) got its first real caller** — existed since the original design-system pass, unused until a card needed a plain divider between its main content and a secondary action.
- **Nothing was invented that isn't real.** Every number on this page (subscription tier/status, renewal recap stats, data-overview counts, notification categories) comes directly from an existing, already-tested backend endpoint; no new endpoint, field, or business rule was added anywhere.

## Progress (2026-08 — sixth product page, and the first genuinely new one)

Every other page in this redesign effort migrated a route that already existed. Progress is different: `/progress` did not exist before this session, in either the old or new frontend, and — this matters — **the backend's own planning document says it isn't supposed to be fully buildable yet.** `docs/99-Audits/PHASE0_EXECUTION_PLAN.md`'s milestone table (M8, "Progress Screen & Cross-Entity History Aggregation") lists a **hard** dependency on M5 (`GET /roadmap/history`, mirroring the existing `skill-gap-analysis/history` endpoint — not built) and a soft dependency on M7 (Change Awareness / diffing — not built either), and says explicitly: "Progress is most meaningful once regeneration is real and change explanations exist to embed." None of M5, M6, or M7 has landed. Given the explicit instruction not to change backend architecture, this pass could not close M8 as that document defines it — and did not try to. What it built instead is the most honest, real Progress experience obtainable purely from data that already exists, with every gap that leaves documented here rather than papered over.

**What's real on this page, and where each number comes from:**
- **Career Readiness** — current confidence (`GET /skill-gap-analysis/current`, reusing `ConfidenceBadge`), open-gap count (same response), roadmap completion (`GET /settings/renewal-recap`'s `roadmap_items_completed_count`/`_total_count` — the same numbers Settings already shows, not recomputed differently). No composite "readiness score" was invented — several real, separately-labeled metrics are shown side by side instead of blended into one fabricated number, consistent with this project's standing RAI stance that a computed signal must be traceable to something real, not synthesized for a nicer-looking UI.
- **AI Insight** — the current analysis's own `summary` field, shown verbatim, clearly attributed to the AI (not a client-computed observation dressed up as one).
- **Skill Improvement Over Time** — `GET /skill-gap-analysis/history`, called here for the first time by any frontend page in this codebase. Rendered as a Roadmap-style vertical timeline, oldest to newest (the backend returns newest-first; sorted client-side), each version showing its confidence and gap count, with a small `Progress` bar scaled to the largest gap count across all versions — an honest, transparent visual (a bigger bar means more gaps then, not a fabricated trend line), and if only one version exists, the page says so explicitly instead of implying a trend from a single data point.
- **Completion Metrics** — reuses the exact same `RenewalRecapRead` numbers Settings shows, via the newly-shared `StatCard`.
- **Milestones ("Your journey")** — built from `GET /notifications`, grouped Today/Yesterday/Earlier (via the newly-shared `lib/datetime.ts`) and rendered as a real connected timeline (Roadmap's dot-and-line visual language, not Notifications' card-list treatment) with the shared category icon/color per entry.

**What isn't real, stated plainly:**
- **There is no roadmap version history on this page**, despite "Roadmap history" being an explicit requested focus area. `GET /roadmap/history` does not exist (confirmed against the execution plan's own M5 entry) — only the *current* roadmap is ever queryable. What this page shows instead is what `roadmap_updated` notifications reveal: that an update happened, and when, and (from the notification's own message text) which version number it became — never a real snapshot of what a past version actually contained, and never a diff between versions. This is the single largest gap between what was asked for and what the current backend can honestly support without a new endpoint.
- **No Change Awareness.** "What changed and why" between two versions (M7) doesn't exist anywhere in this stack yet, so no version-to-version diff appears here, on Skill-Gap Analysis, or on Roadmap.
- **No fabricated milestone entity.** "Milestones" here are notifications, re-styled — there is no distinct backend "Milestone" concept being read from; this is presentation synthesis over real data, not a new business concept invented client-side.

**Motivation without gamification, deliberately**: no streaks, points, badges, achievements, or leaderboards anywhere on this page — only real counts, percentages, and the AI's own words, which is what the brief asked for and what this project's whole design language has consistently avoided elsewhere too.

**New shared modules, not duplicated code** (see Structure below for the full list): `lib/datetime.ts` and `lib/notification-categories.ts` (both extracted from Notifications), `components/stat-card.tsx` and `components/section-error.tsx` (both extracted from Settings), `lib/server-fetch.ts` (the `Fetched<T>`/`fetchSection`/`fetchOptionalSection` Server Component helpers, also extracted from Settings). Notifications and Settings were both updated to import from these instead of keeping their own copies, and both were re-verified (`tsc`/`eslint`) after the change.

## Accessibility pattern (`/profile` is the one remaining pre-migration reference implementation)

Established prior to the design-system work, not yet retrofitted on `/profile` or `/onboarding` (see Known gaps): every form input has an explicit `<label htmlFor>`/`id` pair; validation errors are wired to their input via `aria-invalid`/`aria-describedby`; a visually-hidden (`sr-only`) `aria-live="polite"` region announces async status changes (submitting, success, failure) to assistive technology without requiring a sighted scan of the page; focus is moved programmatically to newly-appeared result content after an action completes (a `ref` + `tabIndex={-1}` + `.focus()`, not just a visual scroll); collapsible content uses native `<details>`/`<summary>` rather than a custom expand/collapse widget, since the native element is keyboard-operable and screen-reader-announced with zero ARIA authoring required; destructive actions get an explicit confirmation step; toggle-style controls (notification-category mutes) expose their state via `aria-pressed` rather than color alone. **Now migrated**: CV Feedback's round deletion and Settings' "clear profile data" both moved from a bare `window.confirm()` to a themed, Radix-backed `Dialog` — still an explicit confirmation step, just no longer an unstyled native browser dialog. Settings' account deletion deliberately did **not** move to a `Dialog` — it keeps its stronger type-to-confirm-your-own-email step, which remains the right call for that specific, highest-stakes, truly irreversible action; a lighter one-click `Dialog` confirmation would be a real regression there, not an improvement.

A small backend addition (`PATCH /notifications/read-all` or similar) would unblock a real implementation.

The lookup tables exist so a future backend category "just works," not to imply those types already occur.
