# CareerOS — Implementation Changelog

Tracks implementation milestones across `frontend/`, `backend/`, and `ai/` together, since most features cut across all three. Architecture-level history (PRD, SAS) is tracked separately in `docs/01-Product/CHANGELOG.md` and `docs/02-Solution-Architecture/CHANGELOG.md`.

## Milestone 3 — Complete Frontend UI/UX Redesign (in progress)

### Notifications migrated to the frozen design system — added

Fourth page migrated under the "design system is now frozen" instruction, same methodology as the prior three. **Presentation only** — no backend/API/database change; every judgment call below was resolved by reading the actual backend rather than assuming, and nothing was fabricated to fill a gap between the requested design and the real data.

**Problems found in the pre-redesign page:** lived outside the `(app)` shell with the same redundant header pattern as the others; no loading state; notifications rendered as a flat, ungrouped list with an absolute `toLocaleString()` timestamp and a bare category badge (`analysis_complete`/`roadmap_updated`/`cv_feedback_complete` shown via a 3-entry label map with no icon or color distinction); no way to tell at a glance what an unread notification was about or where to go next; zero translation/RTL support.

**Reframed as an activity timeline, not an inbox** (the explicit brief): notifications now group into **Today / Yesterday / Earlier** (computed client-side from `created_at`, no backend change), each with a category icon inside a colored circle, a colored `Badge` label, a relative or absolute timestamp depending on the group, and — for the three categories that have an obvious destination — a "View analysis/roadmap/feedback" link. Unread items get a `border-s-2 border-s-primary` accent (reusing the exact treatment already established for "this is AI-grounded, pay attention" content in `ExplainButton`'s answer box and CV Feedback's relevance callout) plus a small unread dot; read items fade to `opacity-70`. Mark-as-read moved from a text button to an icon-only `Check` button with a `Tooltip` (`components/ui/tooltip.tsx`'s first real caller — `TooltipProvider` has wrapped the app since the original design-system pass but nothing had rendered an actual `Tooltip` until now) plus a real `aria-label`, not relying on the tooltip alone.

**Two honest scope decisions, made by reading the backend, not guessing:**
- **Category taxonomy.** The brief asked for seven visual categories (AI Insight, Recommendation, Reminder, Progress Update, Roadmap Update, Goal Update, System Message). The backend's own authoritative list (`NOTIFICATION_CATEGORIES` in `backend/app/schemas/settings.py`, cross-checked against every `notify(...)` call site in `ai_career_center.py`) has exactly **three** real categories: `analysis_complete`, `roadmap_updated`, `cv_feedback_complete`. These were mapped to the closest accurate match — "AI Insight," "Roadmap Update," "Recommendation" respectively, each with its own icon and `Badge` color. The full seven-entry lookup table was still built (so a real future category picks up a treatment with zero frontend change), but no notification of the other four types was invented to make the design look more populated than the data actually is; an unrecognized category defensively falls back to a generic "System Message" treatment rather than crashing.
- **"Mark all as read."** The backend has one mutation — `PATCH /notifications/{id}/read`, scoped to a single notification — and no bulk endpoint. Explicitly considered and rejected: looping N individual PATCH requests behind a single "mark all" button would present a non-atomic, partial-failure-prone client-side composition as a single clean action, which is worse and less honest than the feature simply not existing yet. Documented as a real gap with a concrete suggested fix (a small `PATCH /notifications/read-all`-style backend addition) rather than worked around.

**A pre-existing backend inconsistency found, not fixed (out of scope):** both notification endpoints (`list_notifications`, `mark_read`) return bare `dict`/`list[dict]` with no Pydantic `response_model` — the only two endpoints in the entire API built this way; every other router (`ai_career_center.py`, `settings.py`, `profiles.py`) uses a typed `XRead` schema throughout. Also why `NotificationRead.category` stays a plain `string` on the frontend rather than a literal union. Flagged in `frontend/README.md` as a small, independent backend follow-up.

**Timestamps use native `Intl.RelativeTimeFormat`/`Intl.DateTimeFormat`, not translated strings** — "5 minutes ago" needs Arabic plural/dual agreement a hand-written dictionary entry can't express correctly; the native API handles it for free, keyed off the same `Locale` used everywhere else. Zero new dependency, zero new translation keys for time.

**Optimistic local state, same shape as the prior three pages:** notifications are mirrored into local state; marking one read flips its `is_read` immediately and reverts on failure; `router.refresh()` reconciles with the server afterward.

**Verified:** `tsc --noEmit` and `eslint .` both pass clean (inside the running Docker container, after clearing a stale `.next` route manifest and restarting) — one real type error was caught and fixed along the way (an array-literal-inferred `key: string` needed an explicit `Group[]` annotation to narrow to the `"today" | "yesterday" | "earlier"` literal union). Route sweep (`curl`, default + `-b "NEXT_LOCALE=ar"`) across `/`, `/dashboard`, `/skill-gap-analysis`, `/roadmap`, `/cv-feedback`, `/notifications`, `/privacy`, `/terms` — 200/307 everywhere, no 500s, both languages. **Not verified visually**: same standing limitation as the prior three entries — no Chromium binary and no real Clerk keys in this environment, so the grouping, category treatments, and mark-as-read were verified by code review against the now four-times-proven page pattern, not a live signed-in click-through against real notification data.

**Not yet migrated:** Onboarding, Profile, Settings (aside from its Language card). Per explicit instruction, this pass stops here — Settings and the not-yet-built Progress screen are both out of scope for this session.

### CV Feedback migrated to the frozen design system — added

Third page migrated under the "design system is now frozen" instruction, same methodology as Skill-Gap Analysis and Roadmap. **Presentation only**, plus exposing one already-returned backend field the old page silently discarded — no new business logic, no schema change, no agent change.

**Problems found in the pre-redesign page:** lived outside the `(app)` shell with the same redundant header pattern as the other two pre-migration pages; the submission form was a bare `Textarea` with no guidance, no indication of what happens to the pasted text, and no handling for a real, reachable failure mode — submitting with no active goal (`BR-AICC-14`, reachable because Settings supports deactivating a goal) surfaced as a raw error string; feedback items rendered as a flat, undifferentiated list with a plain text category label; **`CVFeedbackItemRead.relevance_to_goal` — returned by the backend on every single item, explaining why that specific piece of feedback matters for the user's specific target role — was never rendered anywhere**; round deletion used a bare, unstyled `window.confirm()`; zero translation/RTL support.

**Structural change, same pattern as the prior two pages:** moved into `app/(app)/cv-feedback/`, split into a Server Component (`page.tsx`) and a Client Component (`cv-feedback-view.tsx`). This endpoint is a list (`GET /cv-feedback`), not a "current single resource" like Skill-Gap Analysis/Roadmap — it 200s with an empty array for a new user rather than 404ing, so there's no `notFound` branch, only a genuine empty-vs-error distinction. Confirmed via `curl -D -` that the moved route still issues a real `307` to `/sign-in` when signed out.

**An honest reinterpretation, not a fabrication — worth flagging on its own.** The brief asked for a clear strengths-vs-improvement-areas split. The backend doesn't support that: `CVFeedbackAgent`'s system prompt is explicit — "Do not rewrite the document — critique only what was submitted" — and its only category axis is `factual_structural` vs `judgment_call` (objective/clear-cut vs subjective/debatable), never a positive "strength" category; the PRD frames this whole capability as Critique/Evaluation (§26.3), not a balanced review. Inventing a strengths section would mean displaying AI-generated praise the agent never actually produced — flatly incompatible with this project's RAI stance (grounded in real data, never fabricated, "never a black box," reinforced everywhere from the FAQ copy to `ConfidenceBadge`'s own doc comment). Implemented instead: the two categories that genuinely exist, presented as two clearly labeled, visually distinct groups (icon + `Badge` color per category, item counts) — the same underlying goal (clear, scannable buckets instead of an undifferentiated list), under accurate names. A real strengths/positives capability, if wanted, is a backend/agent change (a new category, a new prompt instruction), not something the frontend can honestly manufacture on its own.

**`relevance_to_goal` exposed for the first time** — every feedback item now shows a labeled "Why this matters for your goal" callout beneath its note, reusing the exact visual treatment `ExplainButton`'s revealed answer already established (`border-s-2 border-primary bg-secondary/60`) rather than inventing a new one. This is the single highest-value exposed-but-hidden field found across all three pages migrated so far — it's the concrete evidence for the marketing site's own repeated claim ("tied directly to your target role, not generic advice"), and it was sitting unused in the API response the whole time.

**"No active goal" now has a real affordance.** Detected by pattern-matching the extracted error message (`/active goal/i`) rather than a new backend error code — pragmatic and bounded, not a new app-wide error-classification system — and rendered as its own inline callout with a direct link to `/profile` to set a goal, instead of a bare red error string indistinguishable from a real failure.

**`window.confirm()` replaced with a themed `Dialog`** for round deletion — `components/ui/dialog.tsx` (a Radix wrapper) has existed since the original design-system build-out but had never been wired into an actual page; this is its first real caller. Still an explicit confirmation step (unchanged requirement), just no longer an unstyled native browser dialog; focus trap and Escape-to-close come from Radix, not hand-rolled.

**A three-page-old duplication finally addressed:** Skill-Gap Analysis and Roadmap had each independently grown an identical local `extractErrorMessage()` helper (to pull a clean message out of FastAPI's `{"detail": ...}` JSON body, since `apiFetch` only returns raw response text). CV Feedback needed the exact same thing a third time — for both the "no active goal" 400 and round-deletion failures — which is the point at which it stopped being coincidence and became genuinely shared code. Promoted to `lib/api.ts` as `extractApiErrorMessage()`, with both existing call sites updated to import it instead of keeping their own copies.

**Optimistic local state, same shape as Roadmap:** rounds are mirrored into local state; submitting prepends the new round immediately (the `POST` response already contains the full round, no extra fetch needed) and auto-expands + focuses it; deleting removes it immediately and reverts with an error toast on failure; `router.refresh()` reconciles with the server after both.

**Verified:** `tsc --noEmit` and `eslint .` both pass clean (inside the running Docker container, after clearing a stale `.next` route manifest and restarting). Route sweep (`curl`, default + `-b "NEXT_LOCALE=ar"`) across `/`, `/dashboard`, `/skill-gap-analysis`, `/roadmap`, `/cv-feedback`, `/privacy`, `/terms` — 200/307 everywhere, no 500s, both languages. **Not verified visually**: same standing limitation as the prior two entries — no Chromium binary and no real Clerk keys in this environment, so the submission form, the two feedback groupings, the delete dialog, and both themes/languages were verified by code review against the now three-times-proven page pattern, not a live signed-in click-through. This page has the most client interaction of the four migrated so far (submit, delete, per-round expand) — please click through `localhost:3000/cv-feedback` yourself before treating it as fully confirmed.

**Not yet migrated:** Onboarding, Notifications, Profile, Settings (aside from its Language card).

### Roadmap migrated to the frozen design system — added

Second page migrated under the "design system is now frozen" instruction, same methodology as Skill-Gap Analysis: reuse every existing token/component/pattern, UX before visuals, no CRUD feel, real empty/loading/success/error states, subtle animation, accessibility+localization parity. **Presentation only** — unlike Skill-Gap Analysis, Roadmap needed no new backend wiring at all: the pre-redesign page already called every available roadmap endpoint (`GET /roadmap/current`, `PATCH /roadmap/items/{id}/status`, `GET /roadmap/items/{id}/explain`); there is no manual roadmap-refresh endpoint to expose, since a Roadmap only ever regenerates as an automatic cascade of a Skill-Gap Analysis refresh (`_generate_roadmap` in `ai_career_center.py`).

**Problems found in the pre-redesign page:** lived outside the `(app)` shell with the same redundant "Back to Dashboard" header pattern as the old Skill-Gap Analysis page; no loading state; the "CRUD list" feeling was worst here specifically — **all four status buttons (Not started / In progress / Completed / Skipped) rendered simultaneously for every single item**, so an N-item roadmap showed 4N buttons before any content was read; items were plain bordered divs with no visual sequencing, no progress indicator, and no distinction between the step the user should act on next and the rest of the list; the "addresses gap" line read as raw debug text; zero translation/RTL support.

**Structural change, same pattern as the prior two pages:** moved into `app/(app)/roadmap/`, split into a Server Component (`page.tsx`) and a Client Component (`roadmap-view.tsx`). Confirmed via `curl -D -` that the moved route still issues a real `307` to `/sign-in` when signed out.

**A premium planning experience instead of a task list — the visual/UX core of this pass:**
- **Vertical timeline**, not a flat list: each item gets a status-colored connector dot (empty circle / pulsing filled circle / check / skip-forward, per status) joined by a connector line whose segment fills solid `success` green as each step completes — the line itself visually communicates overall progress down the page, not just a separate progress bar.
- **Progress bar + count** ("X of Y steps complete") at the top, using `components/ui/progress.tsx` (a Radix `Progress` wrapper that has existed since the original design-system build-out but had never been wired into an actual page until now) — plus a small "Roadmap complete" success badge that appears only when every item is genuinely `completed` (not merely resolved via `skipped`, which is a real but different outcome).
- **"Up next" highlight**: the first item that is `not_started` or `in_progress` (in existing array order — the backend has no explicit "phase" concept, so none was invented) gets a labeled badge and a soft primary ring, giving real hierarchy between "what to do now" and "what's coming" without fabricating structure the data doesn't have.
- **Status changed via one `DropdownMenu`** (colored dot + current status text + chevron), not four always-visible buttons — the single biggest fix to the page's CRUD feeling. Selecting a new status updates the item optimistically in local state (instant), calls the existing `PATCH .../status` endpoint, reverts on failure with an error toast, and calls `router.refresh()` on success to reconcile with the server — same refresh-then-reconcile shape as Skill-Gap Analysis's Refresh action, applied here to a status PATCH instead of an analysis-refresh POST. Marking an item `completed` specifically shows a success toast (Sonner's second real caller); other transitions update silently since the control itself already shows the new state.
- **Expandable items**: title, status control, and description stay always visible (high-value, worth scanning without a click); the "addresses gap" tag and the `ExplainButton` sit behind a native `<details>`/`<summary>` disclosure per item (keyboard-operable, screen-reader-announced, zero custom ARIA — the same established pattern already used on `/cv-feedback`) — a deliberate split from Skill-Gap Analysis's page-level empty/error `<details>`-free design, chosen because *within* a single roadmap item there's a genuine primary/secondary information split (what to do vs. why/what it addresses) that Skill-Gap Analysis's flatter gap list didn't have.

**A shared-component gap found and fixed while reusing `ExplainButton` here:** it had been dropped into the already-shipped, fully-translated Skill-Gap Analysis page with its own internal strings ("Why?", "Explaining…", "Grounded in:") still hardcoded in English — the rest of that page was translated, but this one shared sub-component silently wasn't. Fixed once, in the shared component (`common.why`/`hideExplanation`/`explaining`/`explainError`, reusing `common.retry`/`common.groundedIn`), which corrects both pages at once. Also switched its remaining physical-direction classes (`border-l-2`, `-ml-2`) to logical (`border-s-2`, `-ms-2`) while already in the file.

**i18n consolidation**: `skillGapAnalysis.version`/`completeOnboarding`/`groundedIn` were promoted to `common.version`/`completeOnboarding`/`groundedIn` — each was needed again, verbatim, by Roadmap, confirming they were shared concepts rather than page-specific copy. `t()`'s `{{var}}` interpolation (added for Skill-Gap Analysis) now also covers multi-variable strings (`roadmap.progress`: "{{completed}} of {{total}} steps complete"). New `roadmap.*` keys (status labels, progress/empty/error copy) are complete, professionally-written Arabic, not machine-translated filler, matching every other dictionary entry in this project.

**Verified:** `tsc --noEmit` and `eslint .` both pass clean (inside the running Docker container, after clearing a stale `.next` route manifest and restarting). Route sweep (`curl`, default + `-b "NEXT_LOCALE=ar"`) across `/`, `/dashboard`, `/skill-gap-analysis`, `/roadmap`, `/privacy`, `/terms` — 200/307 everywhere, no 500s, in both languages. **Not verified visually**: same standing limitation as the Skill-Gap Analysis entry below — no Chromium binary and no real Clerk keys in this environment, so the timeline, status dropdown, expandable details, both themes, and both languages were verified by code review against the now twice-proven page pattern, not a live signed-in click-through.

### Skill-Gap Analysis migrated to the frozen design system — added

First page migrated under the "design system is now frozen" instruction: every subsequent page reuses existing tokens/components/patterns rather than inventing new ones, and follows a fixed 10-point methodology (real user journey, UX before visuals, no CRUD feel, meaningful empty/loading/success/error states, subtle animation, trustworthy AI-output presentation, accessibility+localization parity). **Presentation only**, plus one legitimate wiring of an existing, already-tested backend endpoint that the page previously had no way to call at all (see below) — no new business logic, no schema change.

**Problems found in the pre-redesign page:** lived outside the `(app)` shell with its own ad hoc header and a redundant "Back to Dashboard" button now handled by the Sidebar; had **no way to request a refreshed analysis at all** — `POST /skill-gap-analysis/refresh` (FR-AICC-4) existed on the backend and was already exercised by onboarding, but nothing in the product UI ever called it after that; no loading state; gap items were plain bordered divs with severity shown as raw unstyled text; the "grounded on" line read like debug output; zero translation/RTL support.

**Structural change, same pattern as Dashboard:** moved into `app/(app)/skill-gap-analysis/`, split into a Server Component (`page.tsx` — auth redirect + data fetch, inline `<Suspense>` after the redirect resolves, same reasoning as the documented Suspense/redirect gotcha) and a Client Component (`skill-gap-analysis-view.tsx` — translated rendering plus the page's one interaction). Confirmed via `curl -D -` that the moved route still issues a real `307` to `/sign-in` when signed out, not the degraded client-side fallback a stray `loading.tsx` would cause.

**Refresh action wired in** — the one functional (not just visual) addition this pass: a "Refresh analysis" button on the success state, calling the existing `POST /skill-gap-analysis/refresh` endpoint, showing a loading state on the button, a success/error toast (Sonner's first real caller in this app), and `router.refresh()` to re-run the Server Component fetch afterward. The backend's BR-GAP-1 hard-bar rejection returns a structured JSON `detail` object; since `apiFetch` only surfaces the raw response body text, added a small local `extractErrorMessage()` in the view to pull the human-readable message back out for the toast instead of showing raw JSON — scoped to this one call site, not a new app-wide error-parsing pattern.

**Severity badges, not raw text:** `SkillGapItemRead.severity` reuses the same `high`/`medium`/`low` enum as `confidence`, but the *meaning* is inverted — high severity is bad, high confidence is good — so severity got its own color mapping (`destructive`/`warning`/`success`) and its own translated labels ("Critical gap"/"Moderate gap"/"Minor gap"), rather than reusing `ConfidenceBadge`'s color logic against its opposite semantics.

**Shared-component fixes, made once rather than duplicated per page:**
- `ConfidenceBadge` was hardcoding the English word "confidence" and level name directly in JSX — now `"use client"` + `useTranslations()`, backed by new `common.confidence`/`confidenceHigh`/`confidenceMedium`/`confidenceLow` keys. Fixed in the one shared component (also used by Dashboard and the marketing Product Preview mockup) rather than three times.
- `t()` gained `{{var}}` interpolation (`t("skillGapAnalysis.version", { n: 3 })`) — the first translated string in the app needing an embedded number; infrastructure completion for every future page that needs one, not a one-off.
- `dashboard.retry` promoted to `common.retry` — the label is universal, the surrounding error message is what's legitimately page-specific.
- `Toaster`'s position was hardcoded `"bottom-right"`, unnoticed until its first real caller — fixed to flip to `"bottom-left"` under `dir="rtl"`.

**Two pre-existing lint/config issues fixed while getting back to a clean baseline** (unrelated to this page, but blocking a trustworthy `eslint .` run): `eslint.config.mjs` had no ignore for generated `.next/**` output, so a fresh `.next` build directory produced ~150 unrelated errors from Next.js's own generated type-validator files; added the ignore. `tailwind.config.ts` used a CJS `require("tailwindcss-animate")` inside an ESM/TS config file, which `@typescript-eslint/no-require-imports` flags — converted to a normal `import`.

**Verified:** `tsc --noEmit` and `eslint .` both pass clean (inside the running Docker container, after clearing a stale `.next` route manifest that referenced the just-deleted old page path and restarting the dev server). **Not verified visually**: no Chromium binary and no real Clerk keys are available in this environment (`CLERK_SECRET_KEY`/`CLERK_PUBLISHABLE_KEY` are present in `.env` but empty, so Clerk runs in its own ephemeral "keyless" dev mode) — the four page states, both themes, and both languages were verified by code review against the already-verified Dashboard pattern, not by clicking through a signed-in browser session. See `frontend/README.md`'s "Verified again" note for the exact scope.

**Not yet migrated:** Onboarding, Roadmap, CV Feedback, Notifications, Profile, Settings (aside from its Language card). ### Official Logo System, Theme System, Language System (EN/AR) — added

The user supplied Orbit's official logo and brand board, superseding the prior session's improvised indigo/Inter palette, and requested a complete design-system rebuild derived from it plus full dark/light theming (both hand-tuned, not inverted) and full English/Arabic bilingual support with RTL. **Presentation only** — no backend/API/database/AI/auth change.

**Brand analysis, from the logo:** two intersecting orbit rings (royal purple primary, soft rose secondary) around a purple core; Manrope typeface; pill-shaped UI components; soft purple-tinted shadows; warm, optimistic personality — full writeup in `frontend/README.md`. Every color token (`app/globals.css`, both dark and light) was rebuilt from this palette and independently hand-tuned per theme rather than inverted.

**WCAG contrast — verified programmatically, not assumed:** wrote a small Python script computing relative luminance and contrast ratio (WCAG's own formula) for every text/background token pair in both themes. **Found and fixed three real AA failures before they shipped**: dark-mode `--primary` with white button text was 3.71:1 (needs 4.5:1) — lowered lightness until 5.27:1; dark-mode `--destructive` was 3.82:1 — lowered to 4.89:1; light-mode `--success` and `--warning` were 4.29:1 and 3.57:1 with white text — lowered to 5.89:1 and 5.66:1. Every other pair passed on the first check. This is the first time in this project's design-system work that color contrast was actually computed rather than eyeballed.

**Typography:** switched from Inter to **Manrope** (the logo's own typeface, `next/font/google`) for Latin text, paired with **Cairo** for Arabic — both self-hosted, zero extra network request.

**Shape language:** `Button`, `Badge`, and single-line `Input` moved from `rounded-md` to fully pill-shaped (`rounded-full`), matching the logo's own UI-component reference exactly; `Textarea` and cards moved to a larger, softer radius (`--radius` raised from `0.75rem` to `1.1rem`).

**Logo rebuilt** (`frontend/components/logo.tsx`) — dual crossing orbit rings + rose secondary ring + satellite dots, replacing the prior session's single-ring placeholder mark. New `orbit-spin-slow` keyframe exists for it (opt-in, off by default in persistent nav contexts).

**Full bilingual infrastructure (EN/AR), new this session:**
- `frontend/lib/i18n/` — `config.ts` (locale list, RTL set, cookie name), `messages/{en,ar}.json` (complete, professionally-written dictionaries — not machine-translated filler), `locale-provider.tsx` (`LocaleProvider` context + `useTranslations()` hook, dictionary lookup with an English fallback so a missing key never renders blank or crashes).
- **Locale decided server-side**, not client-side: `app/layout.tsx` reads a `NEXT_LOCALE` cookie via `next/headers` so `<html lang dir>` — and, via a new `generateMetadata`, even the `<title>` — are correct on the very first byte, with zero flash of the wrong direction. This is a deliberately different mechanism from `next-themes`' client-side script-injection approach, chosen because cookies (unlike theme preference, which may only live in `localStorage`) are available during SSR.
- New `frontend/components/language-toggle.tsx`, added to `MarketingNav`, the product `Topbar`, **and** inserted into the existing (not yet redesigned) `/settings` page as a small standalone card — satisfying "switch available in navigation and inside Settings" without redesigning the rest of that page.
- **RTL correctness**: converted physical-direction Tailwind utilities (`left-*`/`right-*`, `pl-*`/`pr-*`, `border-l`/`border-r`, `ml-*`/`mr-*`) to logical properties (`start-*`/`end-*`, `ps-*`/`pe-*`, `border-s`/`border-e`, `ms-*`/`me-*`) across the Sidebar, every marketing section, and the shared `dropdown-menu.tsx`/`dialog.tsx`/`accordion.tsx` primitives — these flip automatically once `dir="rtl"` is set on `<html>`, no per-component override needed. The two things logical properties can't cover — the Sidebar's mobile-drawer slide transform and directional `ArrowRight` icons — got explicit `rtl:` Tailwind variant overrides (`rtl:translate-x-full`, `rtl:rotate-180`). Confirmed flexbox row layouts needed no changes: `flex-direction: row` is itself a CSS logical (inline-direction) property and already flows RTL correctly.

Onboarding, Skill-Gap Analysis, Roadmap, CV Feedback, Notifications, Profile, and the rest of Settings remain English-only, deliberately — the brand direction's own instructions sequence "establish the design system" before "migrate every page," and this pass stops at the former.
