# Phase 0 Execution Plan

**Converts every remaining item in [`PHASE0_IMPLEMENTATION_AUDIT.md`](PHASE0_IMPLEMENTATION_AUDIT.md) into implementation milestones.**

Date: 2026-08-06 · Status: Planning only — **no production code has been written against this plan yet.**

This document takes the audit's 32-item Critical/High/Medium/Low roadmap plus its 8 named bugs and its one un-numbered-but-explicitly-flagged gap (Change Awareness, FR-AICC-6/12 — called out in the audit's Executive Summary as one of the three things blocking an honest "complete" declaration, but never given its own roadmap line item) and regroups all of it into 18 vertical slices. Every audit line item is accounted for somewhere below; none was dropped.

---

## Which bugs should be fixed first

Of the audit's 8 confirmed bugs, three carry real correctness/trust consequences today and should be fixed before any new feature work starts, because new work (especially Milestone 6 and 8) will build on the same code paths:

1. **`RoadmapAgent` confidence bug** (Bug 1) — a currently-shipping, currently-tested-as-passing agent can present `HIGH` confidence on an empty roadmap. This is a live Responsible-AI correctness defect (BR-AI-4/RAI-6), not a cosmetic one, and it sits in code that Milestone 6 (material-change regeneration) will call far more often once auto-regeneration exists — fix it before that traffic increases.
2. **`SkillGapAnalysisAgent`'s misleading `confidence_reason`** (Bug 2) — same category of defect, same urgency, same file family.
3. **Placeholder email shown as real account data** (Bug 5) — the Settings — Account screen's entire purpose is to show correct identity data; showing a fake email on a screen built specifically to show real ones is a user-facing correctness bug, not a nice-to-have.

The remaining five bugs (dead focus-management ref, two-commit partial-cascade, silently-swallowed notification error, discarded `grounded_on`, mislocated `DashboardResponse` type) are real but lower-severity — each is folded into the milestone that already touches its file, below, rather than given its own slice.

## Recommended Execution Order

### Phase 1 — Bug fixes & foundational hardening (parallelizable, ~1–2 weeks)
**M1 → M2 → M3 → M4**, in roughly that priority order but with no hard sequencing between them — all four are independent of each other and of everything else, so a team of more than one can run them fully in parallel. This phase closes every Critical-severity item from the audit except live account-deletion verification's external dependency (a real Clerk secret key, which is a credential-provisioning step, not code).

### Phase 2 — The core missing functionality (sequential within the phase, ~2–3 weeks)
**M5 → M6, M7 in parallel → M8.** M5 is a small, fast prerequisite and should land first. M6 (material-change regeneration) and M7 (Change Awareness) can then proceed in parallel — M7 depends on M5, not M6 — but both should be complete before M8 (Progress), since Progress is most meaningful once regeneration is real and change explanations exist to embed. This phase closes the audit's three headline blocking gaps.

### Phase 3 — Quality gates (parallelizable with late Phase 2, ~1 week)
**M9 → M10**, with **M11** following once M6/M8/M9 are stable. M9 can actually start as soon as Phase 1 frees up capacity — it has no dependency on Phase 2 — so in practice it should run *alongside* Phase 2, not strictly after it; it's placed here because M10 and M11 do depend (softly) on it finishing first.

### Phase 4 — Remaining functional gaps (parallelizable, ~1–2 weeks)
**M12, M13, M14, M15** — none of these blocks or is blocked by any other milestone in this phase; run them in whatever order matches available capacity. M15 benefits from M5/M8 already existing but doesn't hard-require them.

### Phase 5 — Polish & cleanup (~3–5 days)
**M16 → M17 → M18**, in that order, purely because each is lower-risk to do once the code it touches has stopped actively changing.

### Why this order, not another
Bugs first because they're cheap, isolated, and two of them sit in exactly the code path Phase 2 is about to exercise far more heavily. The core-functionality phase comes before quality gates because a test suite or accessibility retrofit built against not-yet-final pages is wasted or duplicated effort — M9 is the one exception explicitly called out as safe to start early, since it touches pages Phase 2 doesn't. Cleanup comes last because refactoring code that's about to change (M6, M7, M8 all touch the AI Career Center router extensively) just creates merge friction.

- Backend: real pytest coverage (SQLite + fake agents/Clerk, per the existing `tests/` pattern), `tsc`/`next lint` clean on any touched frontend code.

- Documentation: `PHASE0-AUDIT.md`, `CHANGELOG.md`, and the relevant package `README.md` updated immediately after each milestone closes, per standing project practice.
- After each phase, re-run the same independent, line-by-line method used in `PHASE0_IMPLEMENTATION_AUDIT.md` (not just a self-report) to get a real, re-measured completion percentage rather than trusting this plan's estimates.

This plan is not itself a permission slip to start writing code — it is the ordering and grouping decision. Confirm scope and priority before Phase 1 begins.
